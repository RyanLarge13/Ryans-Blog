Snippets: Building a Developer Tool While Learning Next.js

A place to save and share useful code became an education in full-stack architecture, authentication, rich editors, database relationships, and the difference between getting something working and understanding why it works.

Why a snippet application?

Most developers accumulate small pieces of code they want to keep: a useful function, a syntax pattern, a solution to an annoying bug. Snippets explored a simple idea—give those pieces of code a home where they could be saved, edited, revisited, and shared.

The repository describes a Next.js application with user accounts and CRUD operations for code snippets, plus likes, favorites, and comments. What looks like a compact productivity tool from the outside involves several connected systems underneath: an editor, authenticated users, server-side operations, and persistent relational data.

From starter project to full-stack application

The earliest recorded commit is dated June 12, 2023 and references Create Next App. A second initial commit followed on July 29. The August history shows work on branding, registration, and sign-in components. By late October, the commit messages become much more specific: syntax highlighting, authentication, server actions, and a functioning code editor.

The application uses Next.js 13 with React and TypeScript. Its package manifest includes Prisma, PostgreSQL support through Prisma's client, Clerk, CodeMirror, Tailwind CSS, and Framer Motion. These choices suggest an application built around server-backed data and an interactive client-side editing experience, rather than a static gallery of code samples.

The editor was its own engineering problem

Plain text input is easy. A useful code editor is not. The dependency list includes CodeMirror's React integration, JavaScript and C++ language support, and a Monokai theme. The commit history documents that work in unusually direct terms: Syntax Highlighting on October 24, Serverside Actions && Code Editor on October 26, and then Finally A Text Editor That Works later that day.

That sequence captures an important distinction: selecting an editor library is only the beginning. The editor still has to fit the component model, handle changing content, and cooperate with the workflow that saves it. The commit messages demonstrate iteration, although they do not tell us every specific bug encountered.

Authentication: changing course instead of forcing it

On October 24, a commit records adding NextAuth. The very next day, another commit is titled Scratching Next Auth, with the explanation that Clerk and its features were being tested instead. The current package manifest and README both identify Clerk as the authentication solution.

This is one of the clearest architectural decisions visible in the history. Authentication is essential to associating saved code with the right user, but building and maintaining an entire identity system can distract from the core product. The switch shows a willingness to reconsider a tool when another option better fits the project at that moment.

It is also a reminder that engineering decisions are contextual. The repository records the switch, but not enough detail to declare one authentication library universally better than the other.

Modeling snippets as connected data

The Prisma schema gives a precise picture of the data model. A Snippet has a UUID, title, summary, code, language, and user ID. Three additional models—Like, Favorite, and Comment—reference snippets and hold their own IDs and user information. The relations specify cascading deletion when a parent snippet is removed.

model Snippet {
  id        String     @id @unique @default(uuid())
  title     String
  summary   String
  code      String
  language  String
  userId    String
  likes     Like[]
  favorites Favorite[]
  comments  Comment[]
}

Simplified excerpt from prisma/schema.prisma; relation annotations omitted for readability.

That structure matters because likes, favorites, and comments are not merely buttons on a page. Each requires durable state and a relationship to both a snippet and a user. The history tracks the application growing into those relationships: User Page && Copy To Clipboard on October 27, Favorites && Likes on October 28, and Comments on October 29.

By October 29–November 1, commits describe deleting snippets, updating snippets, fixing comments and updates, and deleting comments. These are the unglamorous but important operations that turn a demonstration into something users can actually maintain.

Deployment had lessons of its own

One October 24 commit added a postinstall script to generate an up-to-date Prisma client, explicitly mentioning dependency caching on Vercel. That is a useful example of how the production environment can expose assumptions that never become obvious while developing locally.

In November, the history records an experiment with the Vercel Edge Runtime. The final visible commit, dated November 9, reports that the experiment failed because of function-size limits and mentions testing a quicker home-page response. The repository therefore documents a runtime experiment and its limitation, not a successful migration to Edge.

Engineering lesson: A framework feature or deployment runtime is not automatically an optimization. Bundle size, dependencies, platform constraints, and the actual workload determine whether it helps.

What I'd revisit today

Looking at an older project is an opportunity to ask better questions, not just to criticize earlier decisions. The current schema stores user IDs directly on snippets and interaction records; a fresh design review could examine ownership checks, uniqueness rules for likes and favorites, and which constraints should be enforced by the database rather than only by application logic.

I'd also review how the editor manages local state, loading and saving feedback, error handling, and how much code needs to execute in the browser. These are review ideas, not claims that the existing implementation is broken. A proper assessment would require testing the running application and tracing the relevant handlers.

Why Snippets still belongs in my portfolio

Snippets isn't notable because it uses a long list of libraries. It is notable because it connects them around a coherent problem. The application needed users, persistent content, a real editing experience, and ways for people to interact with saved code. The commit history shows those pieces being assembled incrementally, with failed experiments and fixes left visible.

For an early Next.js project, that is meaningful progress. It marks a shift from making pages to designing a system—and learning that the space between those two things is where much of software engineering happens.
